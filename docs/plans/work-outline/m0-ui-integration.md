# Work Outline M0 audit: UI integration points

Scope: `crates/ui` on branch `work-outline-implementation` (read-only audit, nothing edited except this file).
Spec: `docs/plans/work-outline-implementation-specification.md` (UX requirements lines 116-219, acceptance 24-31 at 617-624, M1 scope 639-650).
All paths are relative to `crates/ui/src/` unless prefixed. Line numbers are from the audited tree and will drift.

## 0. Headline findings (read this first)

1. Overview mode is NOT in `ui-settings.json`. It is one entry (`viewMode:canvas`) in a flat JSON string-array file, `overview-ui-flags.json`. "Tolerant enum" here means a pure flag-set parse/serialize pair, not a serde enum. Migration is a few lines plus tests.
2. `overview.rs` (11,090 lines) and `shell.rs` (15,009 lines) are the two hot files. Anything that must edit them should have exactly one owner.
3. The Chat-keyed right pane (diff/files/terminal/browser tabs) only exists on `Route::Chat`. The Overview route renders its own embedded chat panel (shared Shell transcript + composer entities) and a left PR sidebar. An Overview-owned Work Item Details surface therefore does not touch `ChatPanels`/`RightSurface` at all if it is hosted inside `Overview`.
4. `apply_keymap` calls `cx.clear_key_bindings()` (shell.rs:352). Every new binding (including context-scoped outline navigation keys) must be registered from inside `apply_keymap` or a function it calls, or it is wiped on every keymap re-apply.
5. The web-link preference (`open_web_links_in_zeron`) is only honored for transcript markdown links. Overview badges and metadata chips call `cx.open_url` directly and ignore it. Work-item external references need a new Shell-owned opener.
6. Overview List is not virtualized (every row is a child of one `overflow_y_scroll` div). Real virtualization primitives exist elsewhere (`gpui::uniform_list`, `gpui::list` + `ListState`) and should be used for Outline from day one (acceptance 30).
7. A generic text diff data path already exists (`transcript::diff_to_file`, backed by `similar`) but the renderer for a `FileDiff` line (`changes::diff_line_row`) is private. Needs a `pub(crate)` extraction, not a new diff engine.

### Persistence shape (current)
- File: `{data_dir}/overview-ui-flags.json`, constant `UI_FLAGS_FILE` overview_positions.rs:60. Content is a sorted JSON array of strings (`BTreeSet<String>`), loaded by `load_string_set` overview_positions.rs:64-75 (absent or corrupt degrades to empty), saved atomically (tmp + rename) by `save_string_set` 78-95.
- Mode flag: `const VIEW_CANVAS_FLAG = "viewMode:canvas"` overview.rs:752. Present = Canvas, absent = List.
- Related flags in the same file: `hideStale` (754), `showArchived` (756), `groupBy:<dims>` (GROUP_BY_PREFIX 761), `prSidebarOpen` (2297), `prSectionCollapsed:<key>` (2301).
- `ViewPrefs { canvas: bool, hide_stale, show_archived, groups }`: overview.rs:765-771. `view_prefs_from_flags` 776-797 (`canvas: flags.contains(VIEW_CANVAS_FLAG)` at 792). `apply_view_prefs_to_flags` 802-822 (only purges `groupBy:` by prefix, toggles the three booleans individually).
- Load path: `ensure_prefs_loaded` overview.rs:2800-2842 (sets `view_mode` at 2832-2836 only if `!view_prefs_touched`, so a toggle made before `data_dir` exists is not overwritten). Save path: `view_prefs` 2846-2853, `view_prefs_changed` 2862-2869 (read-modify-write of the file so other flags survive).
- Existing tests that pin this: overview.rs ~9274-9374 (round trip, junk flags tolerated, absent = defaults). Doc comment at 719-724 already states unknown/stale flags (`viewMode:myPrs`) are ignored.
- `ui-settings.json` (settings.rs:62, `UiSettings` 610+) holds none of this. No settings.rs change is needed for the mode migration.

### Migration to `OverviewMode { List, Canvas, Outline }` (recommended)
- Replace `ViewMode` with `pub(crate) enum OverviewMode { List, Canvas, Outline }` plus `persist_key()` and `from_flags(&BTreeSet<String>)`; replace `ViewPrefs.canvas: bool` with `mode: OverviewMode`.
- Keep the legacy flag as the Canvas spelling. Add `viewMode:outline` for Outline. List = neither. Reader: no flag = List; `viewMode:canvas` = Canvas (so every existing user's choice survives with zero rewrite); `viewMode:outline` = Outline; both present (only possible after a downgrade/upgrade round trip with an older build that toggles only the canvas flag) = pick one deterministic rule and test it (suggest: Outline wins only if canvas flag is absent, i.e. `canvas` beats `outline`, because the old build can only ever have set canvas deliberately).
- Writer: purge every `viewMode:` entry, then insert the one for the active mode. Old builds read `viewMode:outline` as an unknown flag, i.e. List. No data loss on downgrade.
- Unknown future `viewMode:<x>`: fall back to List, never fail the load.
- Sites to touch: overview.rs 721-724 (doc), 752, 765-797, 802-822, 1901, 2327, 2670, 2747-2749, 2832-2836, 2848, 5811, 5937-5960 (add Outline button), 6154, 6175-6178, 7285/7594 (canvas fns, check they do not assume the enum), tests 9274-9374 and the other test sites that reference `view_mode` (lines 9342, 9363, 9450, 9470, 9517-9545, 10617-11057).

### Canvas positions (must never change on association)
- Store: `overview-positions.json` (overview_positions.rs:23-47, `Positions = HashMap<String,(f32,f32)>` keyed by chat id). In memory `tile_positions: HashMap<String, TilePos>` overview.rs:2330.
- Written only by `save_positions` overview.rs:5781-5793, called on committed tile-drag release (overview.rs:7531 and 7550). Loaded lazily by `ensure_positions_loaded` 5765-5779. Default grid slot assigned by `position_for` 5742-5753 (stride from `flat_grid_stride`, independent of any chat content).
- Grouped canvas positions are recomputed every render and never saved (overview.rs:5779-5780 doc).
- Hazards for the implementer: (a) `save_positions` serializes the whole `tile_positions` map including default-slot entries created by `position_for`, so do not add any code path that calls `position_for`/inserts into `tile_positions` as a side effect of association or filtering; (b) do not feed work-item membership into flat-grid slot assignment; (c) if a "Work item" group dimension is added to `GroupDimension` (overview_grouping.rs:36-96, with `persist_key`/`from_persist_key` 77-96) it only affects grouped canvas, which is not persisted, so it is safe; (d) `OverviewRow::tile_size` (overview.rs:361-366) and `tile_content_height_estimate` (2166-2173) must be kept in lockstep with the tile body; adding a row to the tile without a matching estimate term clips or overflows and also shifts grouped packing (see 3 below for how to avoid this).

### How to add the work-item path chip and "User Action Required"
- Data: add to `OverviewRow` (overview.rs:333) two copied-in fields built inside the cached `rows()` pass (overview.rs:3034-3190), mirroring how `ticket`, `pr_number`, `category` are copied: `work_item_path: Option<WorkItemPathLabel>` (precomputed breadcrumb string + full path for tooltip) and `user_action_count: u32` (0 until M4, but wire it now). Do this in `rows()` so no per-frame work happens; `rows_dirty` (set by `cx.observe(&state)` at overview.rs:2602-2606) already refreshes on any AppState change, so the new watch store notifying AppState is enough.
- Canvas card: add the path chip into the EXISTING status row (7195-7215, which already has a `flex_1` spacer at 7211 and room before the category badge) or into the title/cwd row; do NOT add a new line. Rationale: `tile_content_height_estimate` has no term for it, and the tile has `overflow_hidden` (7080) so a new row would clip. If a new line is genuinely required, extend `tile_content_height_estimate` and its monotonicity tests (overview.rs:10061, 10088) in the same change and accept grouped-layout repack (not saved positions).
- List row: add to the secondary line (6958-6978) next to the status text. It has `truncate` + `flex_1` on cwd, so a `flex_none` max-width chip fits.
- Chat header strips: add a `work-item` item in `metadata_items` (new optional param or a post-pass) so both headers show it; chip action = "reveal in Outline" (new `MetadataAction` variant).
- Attention indicator ("User Action Required"): reuse, do not invent. Two existing vocabularies:
  - Overview: `reference_status_color(ChatIndicator::AwaitingInput)` overview.rs:601-611 (`0xd03b3b` critical red), label via `status_style` 627-635 ("needs input"), `critical` constant used by the My PRs count (overview.rs ~5995, 2985-2991) with border+bold, and the white unread-done ribbon (`card_dimming` 6661-6672, `unread_done_ribbon` 6697-6704).
  - Sidebar: `spaces::status_dot_color` shell/spaces.rs:2081-2100 (theme `accent` for AwaitingInput, `danger` for Errored).
  - Recommendation: in List/Canvas/Outline use the Overview vocabulary (critical red text/dot + same label style as `status_style`), and show the count when >1. Decision for parent: the Overview constants are hardcoded hex, not theme tokens; spec criterion 31 says "active theme... attention indicators". Either keep the hardcoded critical for consistency with existing Overview attention, or migrate that one constant to `theme.danger` for the new indicator only. Do not add a third alert color.
- Dimming: `card_dimming(archived, stale, unread_done)` only. A chat with an open action request must stay full opacity (treat like unread_done: extend the function's inputs and tests).

### Persistence / migration rules
- File: `ui-settings.json`, parsed in `UiSettings::load` settings.rs:1398-1517 via `serde_json::Value` pre-passes, then `serde_json::from_value`; on ANY parse error the WHOLE file resets to defaults (1499). New fields rely on struct-level `#[serde(default)]`, so adding fields to `KeymapConfig` is safe for old files. No `deny_unknown_fields` on settings, so a newer file read by an older build is tolerated.
- New default combos must not collide with a user's existing bindings. Precedent: the "ToggleFiles"/"OpenMyPrs" block settings.rs:1472-1495 sets the new field to `""` (unbound) when its default is already in use by another key; test at settings.rs ~3120-3138. Reuse that loop for any new id with a non-empty default.
- Recommendation: ship all 9 outline commands with EMPTY default combos except possibly Open Outline; the palette is the guaranteed path and avoids collisions with fixed combos (`mod-k`, `mod-shift-o/g/p`, `mod-f`) that conflict detection does NOT cover. If any fixed combo is added, add it to the list in test `overview_navigation_shortcuts_parse_and_do_not_conflict_with_defaults` (shell.rs ~12398).

### Suppression while a text field owns focus
- Modifier chords (`mod-*`) are bound with context `None` and fire globally, including while a `ComposerInput` has focus. That is existing behavior for e.g. `mod-n`. The project's mitigation is `overlay_owns_keyboard` (palette, section dialog, add-space, composer pickers) at action-handler entry.
- Text inputs are `ComposerInput` (composer.rs; `with_context(placeholder, key_context)` :1738). Editing keys are bound only for contexts "Composer", "MessageComposer", "PaletteSearch" (composer.rs:1352-1358, 1507-1600). In the search context navigation keys (bare arrows/enter) are deliberately unbound and bubble to the parent frame (comment composer.rs:1555-1560), so an Outline root that handles bare arrows would steal them from an inline-rename input.
- Therefore bare-key outline navigation must be bound with a key context and a negation predicate, e.g. context `"WorkOutline && !PaletteSearch && !Composer && !MessageComposer"` set via `.key_context("WorkOutline")` on the tree element, inside `apply_keymap`; AND the action handlers must also early-return when an inline editor is active (`editing.is_some()`). Terminal/Browser use the same `.key_context(...)` + context-scoped binding idea (terminal/panel.rs:1760, browser/mod.rs:30-60).
- Escape: Shell resolves Escape for modal surfaces in `capture_escape_surface` shell.rs:8672-8700; closing an Overview-hosted details panel with a dirty draft must go through the discard policy (section 7), not silently drop.

## 6. Attention / notification system

- Single detector in `Shell::on_state_changed` shell.rs:2323-2412: per-chat `SessionNotificationState` (sound.rs:319-358: indicator + `last_completed_turn` + freshness) compared with the previous snapshot in `self.sound_prev` (shell.rs:1676-1678; first appearance seeds silently so boot is quiet). `sound_since` returns `Sound::{Done, Request, Attention}`. ## 9. How the UI consumes engine Watch* streams (pattern for WatchWorkOutline)

- Method constants: `crates/rpc/src/lib.rs` `methods::WATCH_*` (:36-104, 290, 349-352); a new `WATCH_WORK_OUTLINE` is added there (engine/rpc owner). Mutations go through `methods::MUTATE` with `{"op": "...", ...}` (e.g. shell.rs:4825-4838).
- Standing, parameterless watches: `spawn_watch(cx, handle, method, apply: fn(&mut AppState, T) -> bool)` state.rs:2467-2525. Resubscribe loop with 2 s retry, tolerant decode (malformed frame logged and dropped, never fatal), `apply` returns "changed" so `cx.notify()` only fires on real change, stream end -> resubscribe. Registered in `attach_engine` state.rs:1910-1990 into `watch_tasks`; the `*_synced` flags (`spaces_synced`, `chats_synced`) distinguish "empty" from "not yet loaded".
- Parameterized watches with lifecycle reconciliation (the right model for a per-Space `WatchWorkOutline(spaceId)`): `reconcile_change_request_watches` state.rs:1992-2030 computes the desired target set, drops tasks/data for targets no longer wanted (`retain`), spawns missing ones into `change_request_tasks: HashMap<Target, Task>`, and is re-run when Spaces/Devices frames arrive (state.rs:2508-2510 inside `spawn_watch`). `spawn_change_request_watch` 2380-2462 handles `RpcError::UnknownMethod` (mark device unsupported and stop, 2392-2411), other errors with retry, and "preserve latest snapshot during a transport gap" on stream end. Per-selection watch with stale-pump guard: `spawn_queue_watch` 2655-2705 (guards `state.selected_chat == chat_id` before applying).
- Capability gating: `engine_info().supports(capability)` with constants in `crates/proto/src/workspace.rs:8-27` (`capabilities::CURRENT`), used at state.rs:1936-1944 (`MESSAGE_QUEUE_V1`). Remote devices: see per-device `mark_unsupported`/version reporting for change requests (state.rs ~2400-2410; `Device.version`). A `WORK_OUTLINE_V1` capability string belongs next to these; UI rule: unsupported host -> Outline shows an actionable "update/upgrade host" empty state instead of silently showing unassociated chats only.
- Recommended consumer design:
  1. `AppState` gains `work_outlines: HashMap<SpaceId, Arc<WorkOutlineSnapshot>>` (latest composed snapshot, replace-on-frame, not merged client-side), `work_outline_tasks: HashMap<SpaceId, Task<()>>`, and per-Space load state `{Loading, Ready, Unsupported(version), Failed}`.
  2. `reconcile_work_outline_watches` mirrors the change-request reconciler: desired set = Spaces visible in the Overview while mode == Outline (or any chat filter by work item is active), driven by an `AppState::set_work_outline_visible(bool)` like `set_change_requests_visible` state.rs:2036-2041, re-run from `apply_spaces` so a deleted Space drops its task and snapshot (spec 691: Space tombstone suppresses rows).
  3. The frame decode is tolerant (`#[serde(default)]` on every field; unknown enum values -> a fallback variant), reconciling nothing client-side: the engine already emits repaired/quarantined cycles per spec. Keep the last good snapshot across stream gaps; show a stale/offline hint only after N seconds.
  4. Views never subscribe themselves. `Overview` already does `cx.observe(&state)` (overview.rs:2602-2606) and recomputes the cached `rows()` via `rows_dirty`; the Outline view model re-flattens from `Arc` snapshot identity (cheap pointer compare to skip no-op frames) plus the collapsed set.
  5. UI mutations: optimistic echo into the snapshot for rename/reorder (like `replace_chat_title`/`persist_chat_title`) with rollback and a single in-flight guard per item; every mutation carries a client-generated `operationId` (uuid, as `submit_section_dialog` does with `Uuid::new_v4`, shell/sidebar_sections.rs:213-216) so retries are idempotent (spec 87).
  6. Chats stay sourced from `AppState.chats` (WatchChats). The snapshot carries only associations (`chat_id -> work_item_id`); join in the view model. A chat in an association but missing from `chats` is a "dangling" row that must render (acceptance 4), not drop. Note `overview_chats_with_archived` excludes chats with `parent_chat_id` (state.rs:1754): decide how Outline shows child chats (suggest: nested under their parent chat row, or flat under the same work item) so they never disappear.

## 10. Milestone 1 UI file plan

### Design decisions that unblock parallel work
- All new UI code lives in a new directory module `crates/ui/src/work_outline/` registered once in `lib.rs` (`pub(crate) mod work_outline;`).
- Pure, GUI-free logic goes in separately testable files (model/flatten/keyboard/filter/migration helpers). Rendering files depend on them, never the reverse.

## 11. Risks and decisions for the parent

1. Attention color: Overview hardcodes `0xd03b3b`; the sidebar uses theme tokens (accent for AwaitingInput). Pick one for the new indicator (recommend Overview vocabulary inside the Overview, flagged as theme-debt).
2. Palette has no context awareness; several commands need a selected item. Define behavior (open Outline + notice vs hidden entries) before implementing.
3. Empty default combos break `every_default_shortcut_binds_on_this_platform` (shell.rs:12384) unless the test exempts them. Either exempt or assign defaults; decide with conflict test results.
4. Child chats (`parent_chat_id`) are currently excluded from the Overview entirely; define Outline behavior to satisfy acceptance 4 (never disappear silently).
5. Link opening from Overview-hosted details has no "source session": define the fallback (external browser) so the web-link preference is honored where an internal browser is actually possible.
6. `overview.rs` size/compile time: keep new rendering out of it (new module) and keep A's edits there surgical to limit merge pain; any additional contributors must not edit it concurrently.
